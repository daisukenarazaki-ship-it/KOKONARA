# STEP5: QA結果

4つのSkillを以下の4観点で点検した結果。

## 1. 入力が足りない時に止まらないか

| Skill | 入力欠落時の挙動 | 判定 |
|---|---|---|
| ① proposal-writer | 依頼文なし→汎用テンプレをプレースホルダ付きで出力。予算不明→該当行をプレースホルダ化して続行 | ✅ |
| ② seo-article | 文字数・読者不明→仮定を明記して続行。キーワード無しのみ停止（方向違いの全損を防ぐ意図的な例外） | ✅ |
| ③ shop-lp | 店舗名・業種以外は仮定or【要確認】で続行。未回答項目は「質問メッセージ案（最大5個）」に変換 | ✅ |
| ④ daily-ops | 無申告時は「60分・受注なし」のデフォルトで采配 | ✅ |

## 2. 出力形式が安定するか

- 全Skillに固定の出力フォーマット（コードブロック提示）と「この形以外で出力しない」の宣言あり。✅
- チェック工程は表形式を強制し、「問題箇所」欄で空返事（実行した体の✅）を防止。✅

## 3. 誤送信・ファイル破壊・情報流出のリスク

| リスク | 対策 | 残余リスク |
|---|---|---|
| 提案文・納品物の誤送信 | 全Skillで「送信・納品・公開は人間が行う。AIは下書きまで」を絶対ルール化。送信前チェックリストを出力に同梱 | 人間がチェックリストを飛ばすこと。→ チェック4項目だけは毎回読む運用 |
| 雛形・過去案件のファイル破壊 | Skill③「案件ごとに projects/ 新ディレクトリ、雛形は読み取り専用」。リポジトリはgit管理なので復元可能 | 会話AI（非Claude Code）で使う場合はファイル操作自体が無いためリスクなし |
| 情報流出 | 「クライアントの固有情報を他案件・SNSに転用しない」を①②で明文化。実績としてSNSに載せる際はクライアント許可を取る運用（README記載） | profile.md に顧客名を書きすぎないこと（実績は業種+規模で書く） |
| 実績・事実の捏造（信用毀損） | ①「profile.mdにある実績のみ」②「数値・体験談の創作禁止+【要確認】化」③「店舗情報の創作禁止+grep検収」 | — |
| 意図しない課金 | Skill③「費用が発生する提案は明示して人間の判断を仰ぐ」 | — |

## 4. 人間が確認すべき箇所（サマリー）

1. **送信ボタン全般**: 提案文・クライアント返信・納品メッセージ（各Skillのチェックリスト4項目を読んでから）
2. **【要確認】プレースホルダ**: 記事の数値・店舗の住所電話番号など。埋めるのは常に人間
3. **構成案のクライアント承認**: 記事は構成OKをもらってから執筆（Skill②の工程間ゲート）
4. **価格・納期の約束**: Skillは根拠を出すが、守れる数字かの最終判断は人間
5. **金銭まわり**: 入金確認・確定申告はAIに任せない（Skill化対象外として明記済み）

## 既知の限界

- コピペ率チェックは外部ツール（無料のコピペチェッカー）頼み。Skill②の最終確認リストで人間に委譲。
- ココナラ等の規約変更・相場変動には追従しない。週次レビューで人間が気づく前提。
- Skill③の検収のうち「実機スマホでの目視」は自動化不能。最終確認リストに残置。
