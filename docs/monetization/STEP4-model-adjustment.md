# STEP4: 普段使いモデル（Opus 4.8等）向けの調整記録

各Skillを「Fable 5より推論力が控えめなモデルが読んでも迷わないか」の観点で自己点検し、SKILL.md本文に反映済みの内容を記録する。

## 点検観点と施した対策

| 再現できない恐れがあった箇所 | 対策（SKILL.mdに反映済み） |
|---|---|
| 「良い提案文を書いて」だと品質が毎回ブレる | Skill①: 構成を6ブロック固定・順番入れ替え禁止・400〜600字と数値で規定。良い例/NG例を対比で明示 |
| 受注可否の判断を空気で読ませると誤判断する | Skill①: 見送り条件を表にして機械的に判定できる形に（単価下限・YMYL・危険信号の文言まで具体化） |
| 記事でそれらしい数字・体験談を創作しがち | Skill②: 「検証できない数値は【要確認:】にする」を絶対ルール化し、工程3のチェック項目でも二重に検出 |
| 構成→執筆→チェックの工程を混ぜて一気に出力しがち | Skill②③: 冒頭に「どの工程かをまず判定する」分岐表を置き、判定できない場合のデフォルト工程も指定 |
| 雛形(RE:BIRTH)の文言が納品物に残留する | Skill③: 「検索必須ワード6語をgrepしてヒット0件」という機械的に実行できる検収手順に変換。「よく確認する」は禁止語 |
| 既存ファイルを上書きして雛形を壊す | Skill③: 「案件ごとに projects/ 配下に新ディレクトリ、雛形は読み取り専用」を絶対ルール化 |
| 入力が足りないと質問して止まる/勝手に創作する | 全Skill: 項目ごとに「仮定して進める(仮定を明記)」か「これだけは聞く」かを個別指定。例: 記事の文字数は3,000字仮定で進む、キーワード無しだけは止まる |
| ファイルが読めない環境（チャット等）で手が止まる | Skill①④: profile.md/log.mdが読めない場合のフォールバック（プレースホルダ出力・コピペ用1行出力）を明記 |
| チェックリストを「実行した体」で全部✅にする | Skill②③: 「実行せずOKとだけ返すのは禁止」と明記し、結果を表形式（問題箇所の欄つき）で出させる |
| リサーチが「おすすめはAIです」等の感想で終わる | Skill⑤: 検索クエリの型4本・5軸×5点の採点表・出典列挙を義務化。採点表なしの結論を NG例に明記 |
| 台本が「ここで面白い話をする」と丸投げになる | Skill⑥: 「ナレーションは話し言葉で全文書き切る。要約禁止」を手順に明記。秒割り表フォーマット固定 |
| アフィ投稿のPR表記漏れ（法令リスク） | Skill⑥: #PR をキャプション冒頭に置く絶対ルール＋台本側の【PR表記済み】印＋投稿前チェックの三重化 |
| 「月◯万稼げた」系の数字をnoteや動画で創作する | Skill⑥⑦: 「実績数字は log.md / dashboard.md の実数のみ」を絶対ルール化。実績が小さい間は過程を商品にする型を指定 |
| 週次分析で変更点を大量に出して迷走する | Skill⑥モードB: 出力を3行固定・「一度に変えるのは1要素だけ」と明記 |
| 出力形式が呼ぶたびに変わる | 全Skill: 「この形以外で出力しない」と宣言した出力フォーマットをコードブロックで提示 |

## 普段使いモデルでの利用上の注意（人間側の運用）

- Skillの出力に `【】` プレースホルダが残っていたら、**それは正常動作**（創作を防いだ証拠）。埋めるのは人間の仕事。
- モデルがフォーマットを崩したら「SKILL.mdの出力フォーマットに従って」と一言返せば戻る。
- 長い会話の後半でルールを忘れ始めたら、新しい会話でSkillを呼び直す方が早い。
